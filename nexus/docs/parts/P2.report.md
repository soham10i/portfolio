What the cases cover:

- **A3:** each of rows 1–11, with outcome, exact codes and `approvals_required` asserted.
  - Policy caps that lower L3 to L1 (DENY) and to L2 (NEEDS_APPROVAL), and a cap above the level

  - The kill switch winning over every other reason.
- **A4:** the staleness boundary at exactly `max_age_s` (10 s is fresh, 10.001 s is stale). The

- **A6:**
  - Wrong-typed, null, missing, other-entity and undeclared state all give `STATE_UNKNOWN`.

## 2. Deviations from the brief

- **D1. `RISK_HIGH` added to row 10.** A `high` or `critical` action is NEEDS_APPROVAL at any
  autonomy level. The manifest rule `HIGH_AT_L3` already forbids such actions above L2, and the
  policy can only lower autonomy, so this never fires alone today. It is the gate refusing to
  trust that a manifest was validated, and it is the code the P0 example decision already used.
  P2.md row 10 is updated.
- **D2. `cel.py` lives at `src/nexus/cel.py`, not `gate/cel.py`.** `nexus validate` needs it for
  `CEL_SYNTAX`, and contracts must not import the gate. P2.md §1 is updated.
- **D3. A bug found by A6: `parse_path` accepted `[1]` and `a[1]b`.** It now requires a full
  match of `name(.name|[n])*`. No state could reach the gate through this, because only keys
  that match a declared observable are visible, but `test_cel.py` now covers both forms.
- **D4. Missing keys are detected by recording them, not by parsing error text.** The CEL map
  wrapper records every key asked for that does not exist (`StateView.misses`). A precondition
  that errors after a miss is `STATE_UNKNOWN` and names the key; any other error is
  `PRECONDITION_ERROR`.
- **D5. Snapshot.** Planned: one repeatable-read transaction. Built: the kill switch and the
  pack's state are read in one statement, which is one snapshot under read committed. A
  repeatable-read transaction that then appends could fail with serialisation errors against
  other writers to the same session stream. The rate limit is made exact by a per-session
  advisory lock, held for the read–decide–append transaction. Lock order: session lock, then
  stream head. State writers take a key lock, then a stream head, so no cycle is possible.
- **D6. Envelope limits in CEL.** `envelope.limits` is bound in preconditions as doubles, as
  ADR-0011 described. No example uses it yet; the ramp-rate limit is enforced by the connector
  (P3).

## 3. Design notes worth reviewing

- **The gate is a pure function plus a thin I/O shell.** `evaluate` takes no clock and does no
  I/O. `Gate.decide` reads, calls it, validates the decision against the schema (a failure there
  is `GateError`, a bug, never a verdict), and appends. The decision's `latency_ms` covers the
  whole transaction up to the append.
- **What counts as a "decision" for the rate limit.** The limit counts every non-DENY decision,
  NEEDS_APPROVAL included, as P2.md said. It is stricter than counting executions. P3 may want to
  count executions instead, once they exist.
- **`approvals_required` comes from the manifest.** It is the action's `approvers` (default 1),
  and the `CRITICAL_ONE_APPROVER` rule makes critical actions declare 2.

## 6. Suggestions for P3

- **Approvals** should sign `proposal_hash` and be checked against the decision's
  `approvals_required` and the approvers' distinct identities. The decision event is already on
  the session stream, so an approval can reference its `decision_id`.
- **The executor** should re-check the kill switch and re-read state immediately before running,
  because a decision can be minutes old by the time it is approved.
- **Compensation** must never be compensated (ADR-0010). Test a self-compensating action whose
  compensation fails: it should open an incident, not loop.
- **Idempotency:** `proposal.idempotency_key` is not used by the gate. P3 should dedupe
  executions on it.
- **The connector should enforce `envelope.limits`** (the ramp rate), and enforce
  `envelope.params` a second time, as ADR-0009 says.
