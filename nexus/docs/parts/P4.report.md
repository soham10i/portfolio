## 2. Deviations from the brief

- **D1. The echo manifest is copied, not moved.** `contracts/examples/valid/echo.pack.yaml`
  stays where it is, because the P0 example tests use it, and `src/nexus_packs/echo/` holds a
  copy. `test_the_packaged_manifest_is_the_contract_example` fails if the two drift apart.
- **D2. `HOLD` in the trace.** Checks 9–10 (`taint`, `risk_routing`) print as `HOLD`, not
  `FAIL`, because failing them sends the action to a human; it denies nothing. The evidence pack
  is unchanged (`passed: false`); only the human rendering differs.
- **D3. A broken chain still prints the trace.** `nexus trace` prints everything it found, then
  the problems, a warning on stderr and exit 1. That way the reader can see what was edited (in
  the demo, the action now reads "cancel every order").
- **D4. The demo runs `nexus` commands in-process** (`nexus.cli.main`) and prints each as you
  would type it. That avoids a dependency on PATH, and the output is the same. The demo also
  takes `--schema` so the test can use a throwaway schema.
- **D5. Incidents and shadow mode are not separate checks.** The P3 report suggested putting
  them in `checks`. They appear instead in `execution.error` (`EXECUTION_FAILED`,
  `COMPENSATION_FAILED`), in the event timeline (`incident.opened`, `execution.shadowed`), and
  as `execution.status: not_run` for shadowed runs. See Q-P4-1.

## 3. Design notes worth reviewing

1. **What counts as this action's events.** These are:
   - the `decision.made` event;
   - every event on its stream whose payload carries the decision id;
   - the `state.set` events written under those events' trace ids (the observations during
     verification).

   One read transaction gathers them all; `verify_chain` then checks each referenced stream.
2. **`execution` for a refused run.** A step 1 refusal writes no `executions` row. The pack then
   reports `not_run` with the latest refusal code: DENIED, NOT_APPROVED or REJECTED. A refusal at
   re-check has a row, and its code is `RECHECK_DENIED`.
3. **One execution per decision, or none.** If another decision already claimed the idempotency
   key, this decision has no row and shows `not_run`. The other decision's pack shows the run.
   A lookup by key finds the decision that claimed it.
4. **`evidence.py` reads two private helpers from `store.events`** (`_EVENT_COLUMNS`,
   `_row_to_event`), because it needs `pos` ordering across streams. If that is unwelcome, the
   alternative is a small public `EventStore.read_where(...)`.
5. **Loading code from a manifest.** `load_binding` imports only `nexus_packs.*` by default
   (ADR-0014). A third-party pack has to widen `allowed` explicitly.

## 5. Open questions added

- **Q-P4-1.** Should the evidence schema gain explicit `incidents` and `shadow` fields (a
  contract change, v1 → additive), or are `execution.error` plus the timeline enough? Today:
  the latter (D5).
- **Q-P4-2.** What the chain proves. `chain verify` catches an edited, removed or reordered event
  and a cut tail. An owner who rewrites an event *and* recomputes every later hash and the stream
  head would still pass, and the demo does not show that case. Publishing or signing stream
  heads outside the database would close the gap, and belongs with the signing work deferred to
  P8. Is that the intended scope of "tamper-evident" for M1?

## 6. Suggestions for P5

- The planner's output is a proposal. Its `context` items carry the taint the gate already
  enforces, so the planner must mark retrieved documents and tool output as `doc` / `tool`,
  never `user`. The demo's step 3 is that case.
- `nexus trace` is ready to show the plan and the prompt once P5 stores them. Put them in the
  proposal (`plan_id`, already in the schema), or in events on the same session stream that
  carry the decision id, so the evidence builder picks them up without changes.
