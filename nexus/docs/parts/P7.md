# P7 — Knowledge and memory

Date: 2026-10-31. Blueprint §4.3 and the P7 line of §6. Builds on P1 (store), P5 (router) and
P6 (planner and critic).

## Goal

The runtime can answer questions about a project. Every answer sentence is either cited to a
document chunk or a memory, or comes from a live read of an observable. When neither supports
it, the runtime abstains. It also resolves a phrase like "zone two" to a concrete entity id
deterministically. Memory is explicit: it can be inspected and deleted, and a deleted memory is
never retrieved again.

## 0. Hard constraints

1. **Same rules as P5/P6:**
   - only free providers, through the P5 router, with `max_cost_usd=0` on every call;
   - keys come only from the environment;
   - tests and CI use fakes or recorded replies, never a live provider;
   - a live call happens only with `NEXUS_LLM_LIVE=1` and an explicit flag.
2. **Private by default** (ADR-0021). Documents and memories can be private, so `nexus answer`
   only uses `private_ok` providers unless `--cloud` is given. The grounding evaluation is
   synthetic and public and runs with `private=False`, like the P6 eval.
3. **No model call to embed.** The default embedder is local and deterministic (feature
   hashing), so indexing never sends a document anywhere. Model embedders can be plugged in
   later behind the same interface.
4. **Answering acts on nothing.** The answerer reads and cites; it has no gate, executor or
   binding. Nothing the model writes ever becomes a memory: memory is written only by an
   explicit `nexus memory add` (blueprint: "nothing is remembered implicitly").
5. **Retrieved text is data, not instructions.** Chunks, memories and live reads reach the model
   as sources with their own ids. If a retrieved text is passed to the planner, it goes in as a
   `doc` or `tool` context item, never as `user`, so the P2 taint rule holds.
6. **No new dependency.** Postgres full-text search does the lexical half and pgvector (already
   in the `pgvector/pgvector` image used by compose and CI) does the vector half.
   `nexus/` stays standalone.

## 2. Pieces

### 2.1 Chunks and provenance

- **Chunking:**
  - a markdown file is split at headings, then at paragraphs, so a chunk is at most about 900
    characters;
  - each chunk keeps `path` (relative to the corpus root), `line_start`, `line_end`, its
    heading trail and `file_sha256`;
  - it also keeps `commit`, the git HEAD, but only when the file is tracked and unmodified;
    otherwise `commit` is null, so a dirty file never claims a commit it does not match;
  - `chunk_id` is a hash of corpus, path, lines and text, so re-indexing the same content gives
    the same ids.
- **Indexing:** a corpus is re-indexed in one transaction, replacing all its chunks. One
  `knowledge.indexed` event goes to `knowledge/<corpus>`, listing each file's path, sha256 and
  commit, the chunk count and the embedder id.

### 2.2 Hybrid retrieval

The query runs twice and the two rankings are fused:

1. **Lexical:** Postgres full-text search (`english` config), OR of the query's lexemes, ranked
   with `ts_rank_cd`.
2. **Vector:** cosine distance (`<=>`) on a `vector(256)` column, from the local HashEmbedder.

The two ranks are fused with reciprocal rank fusion (k = 60), with ties broken by `chunk_id`, so
the order is deterministic.

- **Vector-only hits** are kept only above a minimum similarity, so an unrelated query retrieves
  nothing.
- **Note:** Postgres FTS is not BM25. ADR-0023 records why, and when to revisit.

### 2.3 Asset graph and entity resolution

Packs declare `assets`. Each asset has these fields:

- `id`: a dotted path; `[*]` marks a family, e.g. `greenhouse.zone[*]`;
- `kind`;
- `name`;
- `aliases`;
- `parent`: an asset declared earlier;
- `count`: required only for a family; its members are 1..count;
- `observables`: ids declared in the same pack; a family's observables use `[*]`.

`AssetGraph.resolve(text)` is a pure function of the text and the graph. It returns mentions,
in text order, each with a span and a status:

| Status | When | Result |
|---|---|---|
| `resolved` | one entity matches | the entity id, e.g. "zone two" → `greenhouse.zone[2]` |
| `ambiguous` | a family with no number ("the zone"), or one alias in two packs | the candidates |
| `unknown` | a family member out of range ("zone 7") | the reason |

Resolution understands:

- digits, number words (one to twenty) and ordinals ("second", "2nd");
- "#2", "number 2" and compact forms ("z2");
- lists ("zones 1 and 3", "zones one, two and four");
- "all zones" and "every zone".

The longest alias wins, and the result does not depend on pack order.

### 2.4 Live grounding

For every resolved entity, each of its observables is read from world state:

- **Fresh:** value, unit and age (now minus the event time that wrote it).
- **Stale:** older than the observable's `max_age_s`. The source gives no value, only "no fresh
  value; the last one is N s old (max M s)", so the model cannot repeat it. The same applies when
  the value is missing.

A question about current values can therefore only be answered from a live read.

### 2.5 Memory tiers

The `memories` table has these columns:

- `id` and `tier` (`session`, `project` or `profile`);
- `scope`: the session id, project id or user;
- `content` and `source` (who said it, where);
- `content_sha256` and `created_at`.

**Events carry no content.**

- `memory.added`: id, tier, scope, source, sha256 and length.
- `memory.deleted`: id, sha256 and reason.

Both go to `memory/<tier>`.

- **Delete:** removes the row in the same transaction as its event. The content is then gone
  from the database and from retrieval, and the hash chain still verifies (ADR-0025).
- **Retrieval:** full-text over `content`, limited to the right scopes. Session memories are
  used only in their session; project memories only for the packs in play; profile memories for
  the user.

### 2.6 The answerer

```
question → resolve entities → live reads ─┐
         → hybrid search (docs) ──────────┼→ sources d1.., m1.., l1.. → answer.compose (model)
         → memory search ─────────────────┘      → checks → answer.critique (model) → answer | abstain
```

1. **No sources at all:** abstain without a model call.
2. **`answer.compose` reply:** `{decision: answer|abstain, reason, sentences: [{text, cites}]}`.
   `cites` is an enum of the source ids shown, with at least one per sentence.
3. **Deterministic checks.** A sentence is dropped when it:
   - cites nothing, or an id that is not a source;
   - cites a numeric live read without stating its value (to the precision written).
4. **`answer.critique`:** marks each sentence `supported` or not. A sentence the critic does not
   mark as supported is dropped (fail closed). The critic can also abstain.
5. **Result:** no sentence left means abstain. An answer records `answer.given` in
   `session/<id>`, with the question, the sentences, their citations, each source's provenance
   (and, for memories, only their id and sha256), the dropped sentences and the model calls.
   `answer.abstained` records who abstained and why.

## 3. CLI

```
nexus knowledge index [--pack greenhouse ...] [--dir PATH --corpus NAME]
nexus knowledge search "text" [--corpus NAME] [--json]
nexus resolve "text" [--pack ...] [--json]
nexus memory add "content" --tier project --scope greenhouse [--source TEXT]
nexus memory list [--tier T] [--scope S] | show ID | delete ID --reason TEXT
nexus answer "question" [--pack ...] [--session ID] [--cloud] [--json]
```

`nexus answer` is local-only unless `--cloud` is given. It prints each sentence with its
citations.

## 4. Evaluation

| Suite | What it checks | Pass |
|---|---|---|
| `evals/assets/resolution.yaml` | 50 phrases → expected mentions | 50/50, identical on a second run and with packs in reverse order |
| `evals/grounding/answerable.yaml` | 20 questions answered from the greenhouse manual or a seeded memory | ≥ 18/20 |
| `evals/grounding/live.yaml` | 10 questions about current values; state is seeded, one value stale, one missing | ≥ 9/10 |
| `evals/grounding/unanswerable.yaml` | 10 questions nothing supports, including one with a document that tries to inject an instruction | ≥ 9/10 |

How each grounding case passes:

- **Answerable:** the answer cites a source whose ref contains the expected ref, and contains
  every expected phrase.
- **Live:** the answer cites the expected observable and states its value. For the stale and
  missing cases, it states no value at all.
- **Unanswerable:** the answerer abstains.

**On every suite:** 100 % of the emitted sentences cite a known source, and every numeric live
citation states the right value. This is checked independently of the answerer's own checks.

The replies are recorded once with `scripts/eval_grounding.py --live --record` (opt-in) and
replayed in tests, `make eval-grounding` and CI. As in P6, a request whose hash differs from the
recording fails.

## 6. Out of scope

- Routing a request between "answer" and "act" (one entry point): P8 with the API.
- Model-based embeddings or rerankers. They plug in behind `Embedder`, and Ollama is the
  obvious local choice; deciding that is Q-P5-2 territory.
- Automatic episode summaries: nothing is remembered implicitly.
- Non-markdown documents (PDF, HTML).
- Letting the planner retrieve on its own. The helper that turns resolved entities into a `tool`
  context item exists; wiring it into `nexus ask` changes P6's recorded prompts, so it waits for
  a re-record.
