# P6 — Planner and critic

**Status:** in progress · **Estimate:** 2 weeks · **Milestone:** M2 (2 of 5 parts)
**Read first:** `../../GOAL.md`, `../INDUSTRIAL_BLUEPRINT.md` §4.4 (cognition), §4.5 (taint) and
the P6 entry; ADR-0009 (structured envelope), ADR-0012 (execution), ADR-0015 (model router).
ADR-0020, ADR-0021 and ADR-0022 are written with this part.

## Goal

From a request in plain words, `Planner.plan(request, session_id)` produces a **typed plan**: a
small DAG of proposals, each for one declared action with concrete parameters. Or it
**abstains**. A separate critic pass checks the plan against the request. Every step goes
through the P2 gate, and the planner stops there: it never executes anything. The LLM proposes,
the runtime disposes.

---

## 0. Hard constraints

Everything from P0–P5 still applies. In addition:

1. **The planner only proposes.** Its output is `gate.decide(proposal)` calls and one plan event.
   It has no executor and no binding. A test asserts that a mock binding sees zero calls and that
   no `execution.*` event appears.
2. **Free providers only, through the P5 router.** Every model call is `Router.generate` with
   `Budget(max_cost_usd=0)`, so a paid provider is refused even if someone gives it a budget.
3. **Private by default.** The planner calls the router with `private=True` unless the caller
   says the request may go to a cloud provider (`private=False`; for `nexus ask`, `--cloud`).
   Gemini's free tier may keep what it receives.
4. **No live calls in tests or CI.** Unit and integration tests use fakes. The eval suite replays
   recorded replies. Recording needs `--live` plus `NEXUS_LLM_LIVE=1`, both by hand.
5. **Taint (blueprint §4.5).** The planner, not the model, builds every proposal's `context`:
   - the request becomes the single `user` item;
   - documents and tool outputs handed to the planner keep their own source (`doc`, `tool`);
   - the model can only point at items by id. It can never create an item, or mark one as `user`
     or `system`.
6. **Keys only from environment variables; no new dependency; nexus/ stays standalone.**

The CLI gains `nexus ask TEXT [--session ID] [--cloud] [--json]`. It plans, sends each step to the
gate, and prints the decisions with their proposal hashes, ready for `nexus approve`. It
executes nothing.

## 2. The loop

```
request ─▶ catalog (L2+ actions of the loaded packs) ─▶ round 1..max_rounds:
    model: plan | abstain ─▶ deterministic checks ─▶ critic: accept | revise | abstain
        checks or critic say revise → feed the problems back, next round
    accept ─▶ map triggers (taint) ─▶ drop steps the critic says were not asked for
           ─▶ gate.decide each step, dependencies first ─▶ plan.proposed event
```

- **Catalog.** Only actions at autonomy L2 or L3 are offered. L0 and L1 actions cannot execute
  anyway. Each entry gives the qualified id, title, description, risk, and the params schema.
  The catalog is deterministic: sorted, and the same packs always produce the same text.
- **The plan reply.** `{decision: plan|abstain, reason, steps: [{id, action, params, rationale,
  depends_on, trigger, uses}]}`. `trigger` is `"user"` or the id of a context item; `uses`
  lists the context item ids the step relied on.
- **Deterministic checks**, before the critic and before the gate:
  - a known action from the catalog;
  - params valid against the action's schema;
  - unique step ids;
  - `depends_on` inside the plan and acyclic;
  - `trigger` and `uses` naming real items;
  - at most `max_steps` steps.
  Any failure is fed back, and nothing is proposed.
- **Critic.** A second, smaller call that sees the request, the catalog and the plan, and
  answers `{verdict: accept|revise|abstain, steps: [{id, requested, problem}], reason}`:
  - `abstain` → the planner abstains;
  - `revise` → another round;
  - on `accept`, a step the critic marks `requested: false` keeps no `user` trigger. It is
    triggered by the tainted item it used, so the gate holds it for a human. If it used none,
    it is dropped as not asked for, together with every step that depends on it.
- **Gate.** Steps are proposed in dependency order:
  - `plan_id` and `depends_on` are set to the dependency steps' proposal ids;
  - the idempotency key is `plan-<plan_id>-<step id>`;
  - the proposer is `agent:planner`.
  A step whose dependency was denied or dropped is `blocked` and never proposed. After a DENY
  the planner does **not** revise to get around the gate (ADR-0020); it reports the reasons.
- **Abstention.** The model abstains, the critic abstains, or `max_rounds` runs out. Nothing is
  proposed, and a `plan.abstained` or `plan.gave_up` event records why.
- **Budgets.** `max_steps` (default 6) caps a plan. `max_rounds` (default 3) caps planning calls,
  with one critic call per round at most.

## 3. Dependencies at execution (ADR-0022)

`depends_on` means "must succeed first" (proposal contract). P6 is the first part that sets it, so
the executor now enforces it. A decision whose dependencies have not all executed successfully
is refused with `DEPENDENCY_PENDING`. This happens before any claim, so the key is not spent and
the step can run once its dependencies have succeeded.

## 4. Evaluation

- **Suites.** `evals/planner/benign.yaml` has 30 tasks over `echo` and `greenhouse`, each with
  the `(action, params)` set it should produce (and `depends_on` where order matters).
  `evals/planner/unanswerable.yaml` has 10 requests that no loaded action can serve.
- **Scoring.** A benign task passes when the proposals the request itself triggered equal the
  expected set (numbers within 1e-6, and each expected `after` dependency present). Extra
  proposals triggered by a context item are allowed: the gate holds them for a human, which is
  what the injected cases test. An unanswerable task passes when nothing is proposed, whether the
  planner abstained or gave up.
- **Recordings.** `scripts/eval_planner.py --live --record` runs the suites once against the
  owner's free Gemini key and saves every reply, keyed by case, call and round, with the
  prompt's sha256. The tasks are synthetic, so there is no private data.
- **Replay.** `test_planner_eval.py` replays the recordings through the real planner, gate and
  store, with no network. A recording whose prompt hash no longer matches fails the test, so a
  prompt change cannot pass on stale replies.

- The full adversarial suite (P9).
