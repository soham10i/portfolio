# P8 — API, SDKs and the approvals inbox

Date: 2026-10-31. Blueprint §5 (surfaces) and the P8 line of §6. Builds on P1–P4 (store, gate,
executor, evidence packs), P6 (planner) and P7 (answerer).

## Goal

Everything the CLI does for one operator, the runtime now does over HTTP for several principals,
each in their own sessions:

- ask or act through **one entry point**;
- see the session's events, live, over a WebSocket;
- approve a held decision from an **inbox** that shows its evidence pack, with an approval
  **signed** over the exact proposal hash.

The blueprint's P8 acceptance:

- a two-session isolation test;
- the approval of a modified proposal is rejected (hash mismatch);
- the P4 demo runs over HTTP.

## 0. Hard constraints

1. **Same rules as P5–P7:**
   - free providers only, every call `max_cost_usd=0`, private unless the request says
     `cloud: true`;
   - keys come only from the environment;
   - tests use fakes and never reach a provider.
2. **Every action goes through the gate.** The API has no path to a binding except
   `Executor.run(decision_id)`, and the executor only runs what the gate decided (and, for
   NEEDS_APPROVAL, what was approved). A proposal that arrives over HTTP is `gate.decide`d like
   any other.
3. **Loopback only.** `nexus serve` binds 127.0.0.1 or ::1 and refuses any other address.
   - Only `localhost`, `127.0.0.1` and `[::1]` are accepted as `Host` headers.
   - There is no CORS.
   - TLS, OIDC and a public deployment are P13. There are no cloud resources.
4. **No ambient credentials.**
   - Every `/v1` route except `/v1/health` needs `Authorization: Bearer <token>`. There are no
     cookies, so a page on another origin cannot act as the user.
   - Tokens are random (256 bits) and stored only as their sha256. No event and no log line
     contains one.
5. **Identity comes from the token, never from the body.**
   - A proposal's `proposer` and `session_id` are set from the principal and the path. A body
     that names someone else is refused.
   - Only a human principal may put a `user` item in a proposal's context. An agent principal
     cannot claim the user asked, so the P2 taint rule still holds over HTTP.
6. **Approvals over HTTP are signed.** The approver's client signs an Ed25519 message naming
   the decision, the proposal hash it computed itself from the proposal it showed, and the
   approver. The server verifies the signature against a key registered to that human. Signing
   keys never leave the client, and public keys are registered by the principal.
7. **New dependencies, permissive only:**
   - `fastapi`, `uvicorn` and `websockets` serve the API;
   - `cryptography` does Ed25519;
   - `httpx` is a dev-only dependency, for the test client.

   All are MIT, BSD or Apache (ADR-0026), and `make licenses` keeps checking. The TypeScript SDK
   has no dependencies; it uses `fetch` and WebCrypto. `nexus/` stays standalone.

Contract change, additive. An evidence pack's `approvals[]` item gets an optional `signature`
(`alg`, `key_id`, `public_key`, `value`, `verified`). The valid example
`set-zone-temp.evidence.json` carries one.

## 2. Pieces

### 2.1 Principals, tokens, roles and keys

| Table | Columns |
|---|---|
| `principals` | `id`, `kind` (`human` / `agent`), `roles`, `token_sha256`, `created_at`, `revoked_at` |
| `principal_keys` | `key_id`, `principal_id`, `public_key` (32 raw bytes), `created_at`, `revoked_at` |
| `sessions` | `session_id` (uuid), `owner_id`, `created_at` |

- **Roles:**
  - `requester`: open sessions, ask, act, read and execute in their own sessions;
  - `approver`: read the inbox, approve and reject. Approving also needs `kind: human`.
- **Management:** principals are managed only from the CLI, which needs database access:
  - `nexus principal add ID --kind human --role approver` prints the token once;
  - `nexus principal token ID` rotates it;
  - `nexus principal revoke ID`.
- **Keys:** a human approver registers a public key with `POST /v1/keys` (authenticated as
  themselves) or `nexus key register`. A principal without the `approver` role gets 403: only
  approvers sign anything.
  - `key_id` is the first 16 bytes of sha256(public key), in hex.
  - Revoking a key stops future approvals with it.
- **Events** go to `auth/principals` and `session/<id>`:
  - `principal.added`, `principal.token_rotated`, `principal.revoked`;
  - `key.registered`, `key.revoked`;
  - `session.opened`.

  They carry ids, kinds, roles, key ids and public keys, never a token or its hash.

### 2.2 Session isolation

- A session belongs to the principal that opened it. Only the owner may:
  - read its events (`GET`, and the WebSocket);
  - send it messages or proposals;
  - execute its decisions.
- Anyone else gets **404**, not 403, so a session's existence does not leak.
- Session-tier memories are already scoped by session id (P7), and an API session id is a
  server-made UUID, so another principal cannot reach them.
- Approvers see only the inbox: open NEEDS_APPROVAL decisions with their evidence packs, never
  the rest of the session. `GET /v1/decisions/{id}` serves an approver the evidence pack of a
  NEEDS_APPROVAL decision, and nothing else in a session they do not own.

### 2.3 One entry point

`POST /v1/sessions/{id}/messages {text, mode: auto|ask|act, cloud: false}`.

- `ask` goes to the P7 answerer, which acts on nothing.
- `act` goes to the P6 planner, whose proposals go to the gate. Nothing executes until the
  owner calls `execute`. Only a human may `act` (an agent principal gets 403 `NOT_USER`): the
  planner cites the message as the user's request, and an agent cannot claim to be the user.
  Agents send typed proposals instead.
- `auto` decides deterministically (`routing.route`):
  - a request for information ("can you tell me…", "show me…", "explain…", "summarize…") is
    `ask`;
  - otherwise a polite imperative ("can you…", "could you…", "please…") is `act`;
  - otherwise a question mark, or a first word that opens a question (what, which, is, does,
    …), is `ask`;
  - anything else is `act`.
- A wrong route is never unsafe. A plan still goes through the gate, and an answer acts on
  nothing. The route is returned with the result, so a client can resend with an explicit
  `mode`. The rule has a 30-case table test (ADR-0029).

### 2.4 Signed approvals

```
message = JCS({"v": "nexus.approval/1", "decision_id": D, "proposal_hash": H,
               "approver": {"kind": "human", "id": P}})
signature = Ed25519(private key, message)
```

`POST /v1/decisions/{id}/approve {proposal_hash, key_id, signature}`. The server checks, in
order, inside the decision's lock, with nothing written on a refusal:

1. The principal has the `approver` role (403), and the decision is one it may see (404).
2. The decision is open: NEEDS_APPROVAL, the approver is human, not rejected
   (`REJECTED`), not executed (`ALREADY_EXECUTED`).
3. The key is theirs and not revoked (`UNKNOWN_KEY`).
4. The signature verifies over the hash they sent (`BAD_SIGNATURE`).
5. The P3 rules: `HASH_MISMATCH`, `PROPOSER`, `DUPLICATE`.

- The `approval.granted` event stores the signature, key id and public key, so the evidence
  pack can re-verify it from the log alone.
- When approvals are counted (`approval_state`), a signature that is present must verify, or
  the approval does not count.
- `nexus approve --key PATH` signs from the CLI. Without `--key`, the approval is unsigned, as
  in P3, and the evidence pack says so (Q-P8-1).
- **The SDKs and the inbox compute the hash themselves** from the proposal they display (JCS +
  sha256, as `gate.proposal_hash`). They never copy the server's hash. If the proposal they
  were shown is not the one decided, the hash differs and the approval is refused with
  `HASH_MISMATCH`.

### 2.5 HTTP surface (`/v1`)

| Method and path | Who | What |
|---|---|---|
| `GET /v1/health` | anyone | `{ok, version}` |
| `GET /v1/me` | any principal | id, kind, roles, keys |
| `POST /v1/keys` / `DELETE /v1/keys/{key_id}` | human approver | register or revoke own public key |
| `POST /v1/sessions` · `GET /v1/sessions` | requester | open, list own |
| `POST /v1/sessions/{id}/messages` | owner | the one entry point (§2.3) |
| `POST /v1/sessions/{id}/proposals` | owner | a typed proposal straight to `gate.decide` |
| `GET /v1/sessions/{id}/events?after=N` | owner | the session stream |
| `WS /v1/sessions/{id}/events` | owner | the same, live; the first message is `{"token": …}` |
| `GET /v1/decisions/{id}` | owner or approver | the evidence pack and whether its chain verifies |
| `POST /v1/decisions/{id}/execute` | owner | `Executor.run`, whose checks are unchanged |
| `GET /v1/inbox` | approver | open NEEDS_APPROVAL decisions with evidence packs |
| `POST /v1/decisions/{id}/approve` · `/reject` | approver, human | §2.4 |
| `GET /inbox` | anyone | the static inbox page; data needs a token |

- **Errors** are `{"error": {"code", "message"}}`:
  - 401 no or bad token;
  - 403 role;
  - 404 not found or not yours;
  - 409 refused by the approval rules;
  - 422 invalid body.
- **Headers:** every response carries `X-Content-Type-Options: nosniff`,
  `Referrer-Policy: no-referrer` and `Cache-Control: no-store`. The inbox page adds a strict
  CSP: `default-src 'self'`, no inline script, `frame-ancestors 'none'`.

### 2.6 SDKs

- **Python, `nexus.sdk`:**
  - `Client(base_url, token)` uses `urllib` only;
  - `Signer` generates, saves (0600) and loads an Ed25519 key;
  - `proposal_hash(proposal)`.
- **TypeScript, `sdk/ts/nexus.ts`:**
  - the same client over `fetch`;
  - Ed25519 through WebCrypto;
  - its own JCS, for the values JSON can carry.
- Both SDKs are tested against `sdk/vectors.json`: canonical JSON, proposal hashes and the
  approval message. The vectors are generated by and checked against the Python
  implementation.

### 2.7 The inbox

`/inbox` is three static files, with no framework and no build step.

- **The token** is pasted once and kept in `sessionStorage`.
- **The key:** the page generates a non-extractable Ed25519 key in IndexedDB and registers its
  public key.
- **Each item** shows the decision's evidence pack:
  - action and parameters;
  - rationale and context sources (tainted ones marked);
  - the gate's reasons;
  - approvals so far;
  - whether the chain verifies.
- **Approve** recomputes the hash locally, shows it beside the server's and refuses to sign if
  they differ. Reject needs a reason.
- **Rendering:** all text goes in through `textContent`, never `innerHTML`, because proposal
  text can come from documents.

### 2.8 `nexus serve`

```
nexus serve [--host 127.0.0.1] [--port 8765] [--pack echo --pack greenhouse]
```

- It loads packs and bindings as the CLI does, and the same `Policy()`.
- It reads `NEXUS_DB_URL`, `NEXUS_DB_SCHEMA` and the anchor variables.
- It refuses a non-loopback `--host`.

## 3. The demo over HTTP

`scripts/demo_http.py` (`make demo-http`) uses a fresh schema and starts the server in-process
on a free loopback port. Two principals are made: `operator` (requester) and `alice` (human
approver), and alice registers a key. Then, using only the Python SDK:

1. ALLOW → execute → verified.
2. DENY: the executor refuses.
3. NEEDS_APPROVAL (a document-triggered proposal) → execute refused (`NOT_APPROVED`).
4. alice signs the hash of a *modified* copy of the proposal → 409 `HASH_MISMATCH`.
5. alice signs with a key that is not registered to her → 409 `UNKNOWN_KEY`.
6. alice signs the hash of what she was shown → approved → execute → verified.
7. alice cannot read operator's session (404), and operator cannot approve (403).
8. The evidence pack over HTTP shows the signed approval, verified, and its chain intact.
9. `nexus chain verify` passes.

## 5. Out of scope

- OIDC, TLS, rate limits, a public deployment and multi-tenant packs: P13.
- Recovering an execution left `running` by a crashed process (ADR-0012). It is still flagged;
  the long-lived server makes it more likely, and P13 (ops) takes it.
- Requiring signatures for CLI approvals (Q-P8-1).
- An MCP server and voice: P10 and later.
- Publishing the SDKs to PyPI or npm. They live in this repository.
