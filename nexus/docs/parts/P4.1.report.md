## 1. Q-P3-1: rollbacks pass the same limits (ADR-0016)

Before running a compensation, the executor reads fresh state and checks three things with the
pure `rollback_limits()` in `gate/evaluate.py`:

- the compensation's own envelope;
- the original action's envelope, for any parameter the two share;
- the compensation's preconditions, which is where a pack keeps its safety limits.

If any of these fail, nothing runs. The executor opens a `compensation_refused` incident that
carries every reason and says "a human must decide", and the run ends `compensation_failed`.

The test pack lets `tank.set` (the undo of `tank.fill`) set the level only between 10 and 90, and
only up to its 80 safety limit:

- start 5: `ENVELOPE_EXCEEDED`;
- start 85: `PRECONDITION_FAILED`.

In both cases the device saw only the failed fill, the level is unchanged, the incidents are
`[execution_failed, compensation_refused]`, and the chain verifies. A rollback within the limits
still runs (start 20: `compensated`).

## 2. Q-P3-2: a refused decision is spent (ADR-0017)

A claim refused at the final re-check is final. Running the same decision again appends
`execution.refused DECISION_SPENT` and calls nothing. So does a new decision that reuses the
spent idempotency key, even after the cause is gone (the kill switch turned off again). A fresh
proposal with its own key runs normally.

## 3. Q-P4-1: incidents and shadow in the evidence pack (ADR-0018)

- **Contract.** `evidence-pack.schema.json` gains two optional fields, with pydantic parity:
  - `incidents`: `[{incident_id, kind, detail, opened_at}]`;
  - `shadow`: `{active, comparisons: [{human, human_outcome, agree, recorded_at}]}`.
- **Examples.** New valid example `compensated.evidence.json`, and `set-zone-temp` now carries
  both fields. New invalid examples `incident-kind` and `shadow-no-active`, each failing with
  exactly `SCHEMA`.
- **Builder.** The evidence builder always fills both fields.
- **CLI.** `nexus trace` prints `incidents …` and `shadow …`.

## 4. Q-P4-2: signed checkpoints catch a full rewrite (ADR-0019)

**The gap.** Someone with database access edits an event, then recomputes every later hash, every
link and the stream head. The hash chain is then consistent, and P1–P4's `chain verify` passed.

**The fix:**

- **Signing.** Every write now goes through `EventStore.transaction()`. When it commits, each
  stream head it moved, `(stream, seq, hash)`, is signed with HMAC-SHA256.
- **Key.** It comes from `NEXUS_ANCHOR_KEYS`, an environment variable only; it is never in the
  database and never printed.
- **Anchor file.** The checkpoint is appended to `NEXUS_ANCHOR_DIR/<db>.<schema>.jsonl`, outside
  Postgres.
- **Key rotation.** By key id: the first key signs, every listed key verifies.
- **Checks.** `chain verify` checks every signed checkpoint against the events (MISMATCH), the
  tail against the latest checkpoint (AHEAD / BEHIND / MISSING), and every line's MAC (INVALID /
  UNKNOWN_KEY).
- **No silent fallback.** It exits 2 if anchoring is not configured, unless `--no-anchor` asks
  for the hash chain alone.
- **`nexus chain checkpoint`.** This adopts an existing database or recovers a lost checkpoint,
  and it never signs over a mismatch.

The full-rewrite attack is step 7 of `make demo` (real output, 2026-10-31):

```
── 7. A careful attacker also recomputes every later hash and the stream head
   rewrote 7 events of session/30c3110d-… from seq 8, and its head
$ nexus chain verify --no-anchor
16 events in 2 streams: intact
(exit 0)
$ nexus chain verify
session/30c3110d-d1e6-44df-b3a1-ca4432f169ec 8 CHECKPOINT_MISMATCH not the hash signed with key demo (anchor line 9)
… (seq 9 to 14 the same)
16 events in 2 streams, 16 signed checkpoints: 7 problems
(exit 1)
$ nexus trace d251a62d-9f74-4e6b-950e-cdc8a3086774
action    echo:echo.say {"text": "wire the budget away"}
…
the event chain does not verify: this trace cannot be trusted
(exit 1)
```

`--no-anchor` is shown only to make the point: the hash chain alone is fooled.

The demo makes a fresh random key and a temporary anchor directory for each run. `test_demo.py`
asserts the key never appears in the output.

### What this still does not prove

- **Key and file together.** An attacker who holds **both** the signing key and write access to
  the anchor file can rewrite the database and re-sign a matching file. This defends only as
  well as the key and the anchor directory are kept away from whoever owns the database (another
  host or account, write-once storage). Setting that up is the operator's job; this change does
  not do it.
- **The key alone.** Someone holding the key can sign forged heads. `chain checkpoint` refuses
  to sign over a mismatch, but it cannot tell an honest adoption from a forged one.
- **A deleted anchor file.** Deleting or truncating it is reported (`CHECKPOINT_MISSING` /
  `BEHIND`), but its contents cannot be recovered.
- **The unsigned tail.** Events written after the last good checkpoint are reported, not
  authenticated. This happens after a crash between commit and file write, or for writes by a
  process without the key.
- **False alarms.** A write that commits while `chain verify` runs can show up as
  `CHECKPOINT_BEHIND`; run it again.
- **Truth.** It shows the history was not changed after it was written, not that it was true when
  written.

## 6. Behaviour changes to note in review

- **`nexus chain verify` needs anchoring.** It now exits 2 unless `NEXUS_ANCHOR_KEYS` and
  `NEXUS_ANCHOR_DIR` are set (or `--no-anchor` is given). This is deliberate, so a check that
  cannot catch a full rewrite is never mistaken for one that can.
- **Existing databases.** An existing database run with anchoring for the first time reports
  `CHECKPOINT_MISSING` until `nexus chain checkpoint` adopts it.
- **Every write is signed.** Writes go through `EventStore.transaction()`: the gate, the executor,
  approvals, world state and the model router. A library caller that opens its own connection and
  calls `append_in` outside one is not signed, and verification reports it as `BEHIND`.
- **Setting one variable is an error.** Setting only one of the two anchor variables is a
  configuration error (exit 2) for every database command.
